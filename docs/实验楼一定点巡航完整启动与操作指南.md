# 实验楼一定点巡航完整启动与操作指南

> 整理日期：2026-07-24  
> 适用车辆：`nano1`  
> Nano 地址：`192.168.31.139`  
> 车端系统：Ubuntu 18.04 + ROS 1 Melodic  
> 导航地图：实验楼一 `first_floor.yaml`  
> 适用功能：固定巡检点、自定义巡检点、有序路线下发、逐点到达确认

## 1. 文档目标

本文把定点巡航涉及的所有启动与操作步骤整理成一条完整流程，包括：

1. 检查小车、网络和急停。
2. 启动 Nano 上的 ROS 导航链与车辆代理。
3. 在 ROS Jazzy 虚拟机中通过 ROS Melodic Docker 运行 RViz。
4. 使用 RViz 的 “2D Pose Estimate” 校准 AMCL 初始位姿。
5. 启动 Windows 后端和前端。
6. 在前端选择多个固定点或创建多个自定义点。
7. 将完整有序路线下发给车端。
8. 根据车端状态确认是否逐点到达。
9. 处理网络、定位、规划和页面异常。

本文不会要求在启动完成后自动让车辆运动。只有操作人员主动在前端点击任务“开始”，路线才会下发。

## 4. 启动前安全检查

开始前必须确认：

- 小车位于实验楼一 `first_floor` 地图覆盖的真实区域。
- 小车实体急停可用。

## 5. 检查三台设备的网络

### 5.1 Windows 检查 Nano

在 PowerShell 中执行：

```powershell
Test-Connection 192.168.31.139 -Count 3
Test-NetConnection 192.168.31.139 -Port 22
Test-NetConnection 192.168.31.139 -Port 11311
```

如果 ROS 和车辆服务尚未启动，`11311` 或 `9000` 暂时不通是正常的；但 ICMP 和 SSH 应当可达。

### 5.2 虚拟机网络必须双向可达

在 Ubuntu 虚拟机执行：

```bash
ip -4 -br addr
hostname -I
ip route
ping -c 3 192.168.31.139
```

曾经出现的虚拟机地址：

```text
192.168.200.134/24
```

这是 VMware NAT 网段。它可能可以主动 `ping` Nano，但 Nano 不一定能把 ROS 话题数据回传到这个地址。ROS 1 不只是访问 Master，还需要节点之间互相回连，因此“能 ping Nano”不代表 RViz 一定能收到话题。

推荐在 VMware 设置中执行：

1. 关闭虚拟机。
2. 打开“虚拟机设置”。
3. 选择“网络适配器”。
4. 选择“桥接模式”。
5. 勾选“复制物理网络连接状态”。
6. 启动虚拟机并重新执行 `ip -4 addr`。

虚拟机应获得与 Nano 同网段的地址。2026-07-31 现场确认结果为：

```text
ens33  192.168.31.143/24
```

`192.168.31.143` 是当前地址，不应永久写死。每次启动 RViz 容器前，都要以 `ip -4 -br addr` 的实际结果为准。曾使用过但已经失效的 `192.168.31.142` 会导致 Nano 无法回连 RViz。

然后在 Nano 上反向测试虚拟机：

```bash
ping -c 3 192.168.31.143
```

只有以下两个方向都成功后，才能启动远程 RViz：

```text
Ubuntu 虚拟机 192.168.31.143 → Nano 192.168.31.139
Nano 192.168.31.139 → Ubuntu 虚拟机 192.168.31.143
```

如果 Nano 反向 ping 不通，先检查虚拟机地址是否已经变化，再检查 Ubuntu 防火墙：

```bash
sudo ufw status
```

防火墙为 `active` 时，可允许 Nano 访问虚拟机：

```bash
sudo ufw allow from 192.168.31.139
```

## 7. ROS Jazzy 虚拟机运行 RViz

### 7.1 为什么不能直接使用 Jazzy

Ubuntu 虚拟机安装的是 ROS 2 Jazzy，而 Nano 使用 ROS 1 Melodic。ROS 2 节点不能直接连接 ROS 1 的 `ROS_MASTER_URI`，因此不能直接用 Jazzy 的 RViz 读取 Nano 的 ROS 1 话题。

当前方案是在虚拟机中运行 ROS Melodic Docker，并在容器中启动 RViz。

### 7.2 拉取镜像

```bash
sudo docker pull osrf/ros:melodic-desktop-full
```

如果出现：

```text
failed to fetch anonymous token
connection reset by peer
```

这是 Docker Hub 网络连接问题，不是 ROS 配置问题。可按顺序处理：

1. 确认虚拟机能访问互联网。
2. 重试 `docker pull`。
3. 检查系统代理是否只配置给浏览器、没有配置给 Docker daemon。
4. 配置可用的 Docker 镜像加速器后重启 Docker。
5. 在网络正常的电脑拉取并导出镜像，再导入虚拟机。

不要因为镜像拉取失败而修改 Nano 的 ROS 配置。

### 7.3 允许容器显示图形界面

在 Ubuntu 虚拟机桌面终端执行：

```bash
xhost +si:localuser:root
```

### 7.4 启动 ROS Melodic 容器

先从桥接网卡 `ens33` 自动读取虚拟机当前地址：

```bash
VM_ROS_IP=$(ip -4 -o addr show dev ens33 | awk '{split($4,address,"/"); print address[1]}')
echo "本次 ROS_IP=$VM_ROS_IP"

sudo docker run --rm -it \
  --network host \
  --env DISPLAY="$DISPLAY" \
  --env QT_X11_NO_MITSHM=1 \
  --env LIBGL_ALWAYS_SOFTWARE=1 \
  --env ROS_MASTER_URI=http://192.168.31.139:11311 \
  --env ROS_IP="$VM_ROS_IP" \
  --volume /tmp/.X11-unix:/tmp/.X11-unix:rw \
  osrf/ros:melodic-desktop-full \
  bash
```

当前现场预期输出为 `本次 ROS_IP=192.168.31.143`。如果变量为空，或者输出的地址不是 `192.168.31.x`，不要启动容器，应先修复桥接网卡。

Docker 容器创建时会固定保存环境变量。虚拟机 IP 变化后，旧容器中的 `ROS_IP` 不会自动更新，必须退出旧容器并使用新地址重新执行 `docker run`。

### 7.5 容器内检查 ROS

进入容器后执行：

```bash
source /opt/ros/melodic/setup.bash
unset ROS_HOSTNAME

echo "$ROS_MASTER_URI"
echo "$ROS_IP"

rostopic list
rostopic echo -n 1 /map_metadata
rostopic hz /lidar/scan_filtered
rosrun tf tf_echo map base_link
```

当前应输出：

```text
http://192.168.31.139:11311
192.168.31.143
```

如果 `rostopic list` 能看到话题，但 `/map_metadata` 一直没有输出，优先检查 Nano 上的 `map_server` 是否启动。

如果能够订阅话题但一直显示 `no new messages`，优先检查：

- 虚拟机是否仍在 NAT 网段。
- `ROS_IP` 是否写成了旧地址。
- Nano 能否反向 ping 虚拟机。
- Nano 的雷达、map_server 和导航链是否真正启动。
- 防火墙是否阻止 ROS 节点随机 TCP 端口。

### 7.6 启动 RViz

```bash
rviz
```

如果出现 OpenGL 问题，确认容器启动参数中存在：

```text
QT_X11_NO_MITSHM=1
LIBGL_ALWAYS_SOFTWARE=1
```

## 8. RViz 配置与 AMCL 初始位置校准

### 8.1 设置 Fixed Frame

在 RViz 左侧 “Global Options” 中设置：

```text
Fixed Frame = map
```

### 8.2 添加显示项

点击左下角 “Add”，依次添加：

| 显示项 | 配置 |
| --- | --- |
| Map | Topic 选择 `/map` |
| LaserScan | Topic 选择 `/lidar/scan_filtered` |
| PoseArray | Topic 选择 `/particlecloud` |
| RobotModel | 使用 TF 显示车体 |
| TF | 用于排查坐标树 |
| Path | 可选，显示全局或局部规划路径 |

LaserScan 可将 Size 调大一些，方便观察激光轮廓和墙体是否重合。

### 8.3 使用 “2D Pose Estimate”

1. 在真实现场确认小车处于实验楼一地图中的哪个位置。
2. 在 RViz 顶部点击 “2D Pose Estimate”。
3. 在地图中对应位置按住鼠标左键。
4. 沿小车真实车头方向拖动箭头。
5. 松开鼠标。
6. 等待 AMCL 更新粒子云。

这一步同时设置：

- 小车在地图中的初始 `x`。
- 小车在地图中的初始 `y`。
- 小车车头相对于地图坐标轴的 `yaw`。

如果位置或方向不准确，可以重新执行，不需要重启 AMCL。

#### 8.3.1 点击后“小车位置不变”的含义和检查方法

“2D Pose Estimate”只向 `/initialpose` 发布一条初始位姿，要求 AMCL 重新计算地图定位，不会给底盘发送速度命令，因此真实小车不移动是正常现象。

它主要修正：

```text
map → odom
```

不会直接修改：

```text
odom → base_link
```

所以查看 `odom → base_link` 数值不变也属于正常现象。RViz 的 `Fixed Frame` 必须设置为 `map`；如果设置成 `odom`，模型可能看起来没有跳转到新位置。

如果 RViz 中的模型、粒子云和 `map → base_link` 都没有变化，在 Nano 上先执行：

```bash
source /opt/ros/melodic/setup.bash
rostopic echo -n 1 /initialpose
```

保持终端等待，再到 RViz 点击 “2D Pose Estimate” 并拖出车头方向。

正常情况下，Nano 应立即收到一条：

```text
geometry_msgs/PoseWithCovarianceStamped
```

收到后继续检查：

```bash
rostopic info /initialpose
rostopic echo -n 1 /amcl_pose
rosrun tf tf_echo map base_link
```

`rostopic info /initialpose` 的 Subscribers 中应包含 `/amcl`。如果 `/initialpose` 已到达 Nano，但没有 AMCL 订阅，应检查 AMCL 是否启动、节点命名空间以及 RViz 工具发布的话题。

如果 Nano 完全收不到 `/initialpose`，优先检查 RViz 容器的 `ROS_IP`。本次现场故障的直接原因是：

```text
虚拟机实际地址：192.168.31.143
旧容器 ROS_IP： 192.168.31.142
Nano ping 192.168.31.142：Destination Host Unreachable
```

RViz 虽然可能主动连接 Master 并看到部分话题，但 AMCL 无法回连 RViz 发布节点，因此收不到初始位姿。解决方法是退出旧容器，以虚拟机当前真实地址重新创建容器。

### 8.4 校准成功判据

必须同时满足：

- RViz 激光点与 `first_floor` 地图墙体基本重合。
- 小车图标位于正确走廊。
- RViz 中车头方向与真实车头一致。
- `/particlecloud` 从大范围散布收敛到小车附近。
- 小车轻微移动后定位没有明显跳变。
- `rosrun tf tf_echo map base_link` 能持续输出。

未满足时不要点击前端“开始”。

| LAB-P03 | 东北转角 | `(19.954, -1.907, -1.571)` |

## 12. 创建自定义巡检点有序路线

1. 在“点位与路线”顶部选择“自定义点位”。
2. 页面自动显示 `first_floor` SLAM 栅格地图。
3. 在白色自由通行区域依次点击目标。
4. 每次有效点击会创建“自定义点1、2、3……”。
5. 在路线列表中调整顺序。
6. 为每个点选择到点朝向。
7. 点击“创建任务”。

页面会拒绝以下点击：

- `first_floor` 覆盖区外。
- 黑色墙体。
- 灰色未知区域。
- 距离障碍物过近的位置。
- SLAM 图像尚未加载完成时的点击。

页面显示的 `map (x, y)` 是最终下发给 ROS `move_base` 的坐标。

## 13. 下发路线与逐点确认

创建任务不会立即让车运动。只有点击任务行中的“开始”才会下发。

点击“开始”后：

1. 前端把完整有序路线一次发送给后端。
2. 后端把路线转发到 Nano 的 `/navigation_route`。
3. 车端验证整条路线并生成唯一 `execution_id`。
4. 车端只向 `move_base` 发送第一个目标。
5. 只有第一个目标返回 `GoalStatus.SUCCEEDED`，才发送第二个目标。
6. 任一点失败，后续点不再发送。
7. 前端每秒查询执行状态。
8. 只有 `reached_count == route_total` 且车端状态为 `completed`，前端才显示任务完成。

车端独立检查：

```bash
curl http://192.168.31.139:9000/navigation_route/status
```

重点字段：

| 字段 | 含义 |
| --- | --- |
| `execution_id` | 本次路线唯一编号 |
| `active` | 路线是否正在执行 |
| `state` | `queued`、`moving`、`arrived`、`completed`、`failed`、`cancelled` |
| `route_index` | 当前目标序号 |
| `route_total` | 总点数 |
| `reached_count` | 已被 `move_base` 确认成功的点数 |
| `point_id` | 当前点位编号 |
| `results` | 每个点的执行结果 |
| `last_error` | 最近错误 |

## 14. 暂停、取消和紧急停车

### 14.1 前端暂停

点击任务“暂停”会请求车端取消当前路线。当前 `move_base` 目标被取消后，后续点不会继续发送。

### 14.2 API 取消

需要指定执行编号时，可调用后端：

```text
POST /api/vehicle/navigation-route/cancel
```

### 14.3 车端停止

```bash
curl -X POST http://192.168.31.139:9000/stop
```

### 14.4 ROS 零速度

```bash
source /opt/ros/melodic/setup.bash
export ROS_MASTER_URI=http://192.168.31.139:11311
rostopic pub -1 /cmd_vel geometry_msgs/Twist '{}'
```

紧急情况必须优先使用实体急停。网页、HTTP 和 ROS 停止命令都不能代替硬件急停。

## 15. 正常停止服务

确认：

- 路线 `active=false`。
- 小车已经完全停止。
- 当前没有人依赖 RViz 或前后端。

然后关闭前端和后端终端：

```text
Ctrl+C
```

退出 RViz 和 Docker：

## 16. 常见问题

### 16.1 虚拟机可以 ping Nano，但 RViz 没有数据或 2D Pose Estimate 无效

最常见原因是网络只有“虚拟机到 Nano”单向可达，Nano 无法回连，或者 Docker 仍保存着虚拟机的旧 `ROS_IP`。

先在虚拟机检查当前地址：

```bash
ip -4 -br addr
hostname -I
ip route
echo "$ROS_MASTER_URI"
echo "$ROS_IP"
```

再从 Nano 反向检查虚拟机当前地址。2026-07-31 现场地址为：

```bash
ping -c 3 192.168.31.143
```

判断方法：

| 检查结果 | 结论 | 处理 |
| --- | --- | --- |
| 虚拟机不是 `192.168.31.x` | 仍在 NAT 或错误网卡 | 改用 VMware 桥接模式 |
| Nano 无法 ping 虚拟机 | 不能建立 ROS1 节点连接 | 检查桥接、防火墙和地址冲突 |
| 容器 `ROS_IP` 与 `ens33` 不一致 | 容器使用旧地址 | 退出并重新执行 `docker run` |
| `/initialpose` 没有到达 Nano | RViz 发布链路不通 | 修复双向网络和 `ROS_IP` |
| `/initialpose` 到达但没有 `/amcl` 订阅 | AMCL 或话题配置问题 | 启动 AMCL，检查命名空间和话题 |

不要只根据 `rostopic list` 能否列出话题判断网络正常。`rostopic list` 只证明容器可以访问 ROS Master，不能证明 Nano 能访问 RViz 节点。

修复后，在 Nano 运行：

```bash
rostopic echo -n 1 /initialpose
```

然后再次使用 RViz 的 “2D Pose Estimate”。收到消息后，检查：

```bash
rostopic echo -n 1 /amcl_pose
rosrun tf tf_echo map base_link
```

### 16.2 `/map_metadata` 没有输出

Nano 上检查：

```bash
rosnode list | grep map
rostopic info /map
rostopic echo -n 1 /map_metadata
```

如果没有 `map_server`，启动 `navigation.launch` 并加载 `first_floor.yaml`。

### 16.3 `/lidar/scan_filtered` 显示 `no new messages`

Nano 上检查：

```bash
rostopic hz /lidar/scan
rostopic hz /lidar/scan_filtered
rosnode list | grep lidar
ls -l /dev/n10p_lidar
```

如果原始 `/lidar/scan` 正常但过滤话题没有数据，检查 `laser_scan_angle_filter` 节点。

### 16.4 RViz 中激光和地图不重合

可能原因：

- 2D Pose Estimate 的位置错误。
- 箭头方向与真实车头相反。
- AMCL 粒子云未收敛。
- TF 中 `base_link` 或 `laser_link` 方向错误。
- 小车不在当前地图覆盖的真实区域。

重新设置初始位姿，并观察：

```bash
rosrun tf tf_echo map base_link
```

### 16.5 点击自定义路径点没有反应

检查：

- 是否选择了“自定义点位”，而不是“固定点位”。
- SLAM 图是否加载完成。
- 点击位置是否为白色自由区域。
- 是否点击在墙体、未知区或覆盖区外。
- 页面是否显示红色拒绝原因。
- 浏览器是否已经 `Ctrl+F5` 刷新到最新版。

### 16.6 路线返回 409

通常表示：

```text
a navigation route is already running
```

先查询当前路线，确认后取消：

```bash
curl http://192.168.31.139:9000/navigation_route/status
curl -X POST \
  -H 'Content-Type: application/json' \
  -d '{}' \
  http://192.168.31.139:9000/navigation_route/cancel
```

### 16.7 `move_base action client is not available`

检查：

```bash
rosnode list | grep move_base
rostopic list | grep move_base
rosrun actionlib axclient.py /move_base
```

确认 `move_base` 已启动且车端代理连接的是同一个 ROS Master。

### 16.8 路线已接收但小车不运动

依次检查：

1. 实体驱动使能。
2. AMCL 和 TF。
3. 目标是否位于自由空间。
4. 全局和局部 costmap。
5. TEB 参数是否正确加载。
6. `/navigation/cmd_vel_raw` 是否有非零速度。
7. `/cmd_vel` 是否经过安全限速器正常输出。

```bash
rostopic echo /move_base/status
rostopic echo /navigation/cmd_vel_raw
rostopic echo /cmd_vel
rosparam get /move_base/base_local_planner
rosparam get /move_base/TebLocalPlannerROS/max_vel_x
```

### 16.9 前端进度不再更新

不要根据页面停留时间判断路线是否完成。直接查询 Nano：

```bash
curl http://192.168.31.139:9000/navigation_route/status
```

若车端仍在执行，先恢复前后端网络；若车端已失败，查看 `last_error` 和 `results`。

## 17. 首次实车验收清单

建议只选择两个相邻点，并记录以下结果：

- [ ] Nano、Windows、虚拟机双向网络正常。
- [ ] RViz 容器中的 `ROS_IP` 与虚拟机 `ens33` 当前地址一致。
- [ ] Nano 能收到 RViz 发布的 `/initialpose`。
- [ ] `/map_metadata`、雷达、里程计有数据。
- [ ] RViz 激光与地图墙体重合。
- [ ] 粒子云收敛。
- [ ] 真实车头与 RViz 箭头一致。
- [ ] 车辆代理状态正常。
- [ ] 路线提交后获得 `execution_id`。
- [ ] 第一个点 `SUCCEEDED` 后才发送第二个点。
- [ ] `reached_count` 按 `0 → 1 → 2` 增长。
- [ ] 前端最终状态与车端一致。
- [ ] 暂停后不会继续发送下一点。
- [ ] 实体急停有效。

只有完成两点低速验收后，才逐步增加路线长度。
